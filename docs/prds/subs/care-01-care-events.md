# [CARE-01] Care Events

> **PRD type:** Sub. Describes the **HOW**, including guardrails.
> Parent: [EPIC-PLANTZ-CARE](../epics/epic-care.md)

## 1. Goal

Watering a plant leaves a row in the database, and logging it takes one tap on the plant
detail page. This is the single most important change in the program: without it, flows F1
and F3 from the dashboard brainstorm have no source data.

## 2. Current State (verified against `main` 4d935f8)

- No table, no endpoint and no UI records a care action of any kind.
- The only trace of "I watered this" is whatever a note happens to say in free text.
- `app/pages/plants/[id].vue` is the detail page: 550 lines, `@nuxt/ui` components
  (`UButton`, `UModal`), data via `useFetch('/api/plants/:id')`, mutations via `$fetch`
  followed by `refresh()`.
- Composables follow one shape: `usePlants()` returns `{ many, fetchMany, getPlantById }`
  over `useState`.
- `db-types.ts` is generated by `scripts/generateTypes.ts` from the live schema. There is
  no npm script that runs it.

## 3. Scope

### 3.1 In Scope

- Migration `005-add-care-events.sql`:
  - `care_type` enum: `watering`, `fertilizing`, `repotting`, `pruning`, `treatment`
    (Q-C1 recommendation: ship all five)
  - `care_events` table: `id` UUID PK, `plant_id` UUID FK to `plants` on delete cascade,
    `type care_type NOT NULL`, `occurred_at TIMESTAMP NOT NULL DEFAULT now()`,
    `note TEXT NULL`, `created_at TIMESTAMP DEFAULT now()`
  - Index on `(plant_id, type, occurred_at DESC)`, which is the access path for both the
    detail page and the INS-01 sampler
- `POST /api/plants/[id]/care` creating one event. Body: `type`, optional `occurred_at`,
  optional `note`.
- `GET /api/plants/[id]/care` listing a plant's events, newest first.
- A `useCare()` composable following the shape of `usePlants()`.
- UI on the plant detail page: a row of care buttons that log with one tap, and a list of
  recent care actions with their dates.
- A "last watered" and "last fertilized" line in the plant header, read from the events.
- An npm script `db:types` that runs `scripts/generateTypes.ts`, plus the regenerated
  `db-types.ts` including `CareEvents`.
- Tests for the endpoint: creating an event, rejecting an unknown `type`, rejecting an
  unknown `plant_id`.

### 3.2 Out of Scope

- Editing or deleting a care event. The table is append-only, see D-C1. If a mis-tap needs
  undoing, that is a follow-up decision, not day-one scope.
- Watering intervals and overdue calculation. That is CARE-04.
- Bulk logging ("watered everything in the living room"). Tempting, but it is a second UI
  with its own edge cases.
- Any change to `notes`. A care note is a column on the event, see Q-C4.
- Metrics. INS-01 reads this table, it does not need changes here.

## 4. Implementation Notes

**Append-only means append-only.** No `PUT`, no `DELETE` endpoint. The table is the
history, and a history that can be edited answers a different, weaker question.

**`occurred_at` defaults to now but is settable.** Q-C3: watering on Saturday and logging
on Monday is the normal case. The API accepts an ISO timestamp; the UI's one-tap path
sends nothing and gets `now()`.

**One tap means one tap.** The primary path is a button per care type that posts and
refreshes, with no modal. A modal for the optional note and date is a secondary path
behind a smaller control. If logging a watering takes three interactions, it will not
happen, and then the whole epic produces an empty table.

**Regenerate the types.** After the migration runs against a local database, run the
generator and commit `db-types.ts`. It is marked auto-generated, so it is a build output
that happens to be committed. Adding the `db:types` script means the next sub-PRD does not
have to rediscover how it works.

**Validation belongs in the endpoint.** `type` must be one of the five. Postgres will
reject an invalid enum value anyway, but a 400 with a clear message beats a 500 with a
Postgres error string.

## 5. Definition of Done

- [ ] `005-add-care-events.sql` exists and is applied by the DEL-01 runner.
- [ ] `POST /api/plants/:id/care` with `{"type":"watering"}` creates a row and returns it.
- [ ] `POST` with `{"type":"nonsense"}` returns 400, not 500.
- [ ] `POST` for a plant id that does not exist returns 404.
- [ ] `GET /api/plants/:id/care` returns the plant's events, newest first.
- [ ] The plant detail page has a care button row, and one tap on Water creates an event
      without a modal.
- [ ] The plant header shows the last watering date, or a clear empty state if there is
      none.
- [ ] `pnpm db:types` exists and regenerating produces a `CareEvents` type.
- [ ] `pnpm test` covers the three endpoint cases above and passes.
- [ ] Deleting a plant deletes its care events (cascade verified).

## 6. Verification

```bash
# Migration applied
psql -h <host> -U <user> -d plantz -c "\d care_events"
# expect: the five columns plus the index

# Create
curl -sX POST http://localhost:3000/api/plants/<uuid>/care \
  -H 'content-type: application/json' -d '{"type":"watering"}' | jq
# expect: 200 and the created row

# Reject
curl -so /dev/null -w '%{http_code}\n' -X POST http://localhost:3000/api/plants/<uuid>/care \
  -H 'content-type: application/json' -d '{"type":"nonsense"}'
# expect: 400

# List
curl -s http://localhost:3000/api/plants/<uuid>/care | jq '.data | length'
# expect: 1

# Cascade
psql -h <host> -U <user> -d plantz -c "DELETE FROM plants WHERE id='<uuid>';"
psql -h <host> -U <user> -d plantz -c "SELECT count(*) FROM care_events WHERE plant_id='<uuid>';"
# expect: 0

pnpm test   # expect: exit 0, the three new cases named
```

## 7. Risks

| Risk | Mitigation |
|------|------------|
| The five care types do not match the real routine | The enum is extendable with `ALTER TYPE ... ADD VALUE` in a later migration. An unused value costs nothing |
| Logging is buried behind a modal and never used | The DoD requires the one-tap path explicitly. This is the failure mode that would make the whole epic pointless |
| A mis-tap creates an event that cannot be removed | Accepted for now. Noted as Q-CARE1-1 |
| `db-types.ts` is regenerated against a stale local schema and loses the new type | Run `db:types` only after the migration has applied locally, and check the diff before committing |
